# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

`MTTextClient` is a single .NET 8.0 executable (C#, ~24 kloc) that talks to MoonTrader Core (MTCore) over encrypted UDP (LiteNetLib + AES-256 derived from a per-profile client token). It exposes the same surface three ways, selected at argv-parse time in [Program.cs](Program.cs):

- **Interactive REPL** — `dotnet run` (no args).
- **One-shot CLI** — `dotnet run -- <cmd>` (e.g. `dotnet run -- algos list`).
- **MCP stdio server** — `dotnet run -- --mcp` (JSON-RPC 2.0 over stdin/stdout).

The MCP server **wraps the REPL**, not the other way around: every `tools/call` lowers to a REPL command string through [MCP/McpServer.cs](MCP/McpServer.cs)'s `MapToolToCommand` and runs through the same `CommandRegistry`. Behavioural parity between REPL and MCP is therefore structural — do not introduce a divergent code path.

## Build / run / test

```bash
# Build everything (main exe + tests + two generator tools)
dotnet build MTTextClient.sln -c Release

# PR-gate slice — no MTCore, no network
dotnet test MTTextClient.sln -c Release --filter "Category=Static|Category=Unit"

# Single test class / method
dotnet test MTTextClient.sln -c Release --filter "FullyQualifiedName~ConfirmGateStaticTests"

# Categories that need a running MTCore reachable on its configured UDP port
MTC_TESTING_ENV=1 dotnet test MTTextClient.sln -c Release --filter "Category=Smoke"
MTC_TESTING_ENV=1 dotnet test MTTextClient.sln -c Release --filter "Category=BenchAll"
MTC_TESTING_ENV=1 MTC_LIVE_TRADES=1 dotnet test MTTextClient.sln -c Release --filter "Category=LiveTrade"
```

CI runs only `Static|Unit` (see [.github/workflows/ci.yml](.github/workflows/ci.yml)). Categories that hit a live MTCore are routed to [.github/workflows/testing-environment.yml](.github/workflows/testing-environment.yml).

## Architecture — three layers

```
Commands/*.cs    ICommand implementations — one per REPL noun (algos, orders, fleet, …)
Core/*.cs        ConnectionManager + per-domain *Store caches + RequestExecutor + RateLimiter
                 + CircuitBreaker + ConnectionPump + ConfirmGate + ToolRegistry
MCP/McpServer.cs JSON-RPC stdio gateway; routes tools/call → MapToolToCommand → CommandRegistry
MCP/EventStreaming.cs  Per-tool metrics, buffered event stream, SSE listener
```

Every domain has a `*Store` (`AlgorithmStore`, `AccountStore`, `CoreStatusStore`, …) that caches subscription-delivered state, so MCP read tools answer from cache instead of blocking on the wire. **When adding a subscription-backed tool, the touch points are the `*Store` and the subscribe/unsubscribe handlers in [Core/CoreConnection.cs](Core/CoreConnection.cs) — not the `Command` class.**

[Core/ConnectionManager.cs](Core/ConnectionManager.cs) owns N `CoreConnection` instances keyed by profile name. Profiles load from `~/.config/mt-textclient/profiles.json` (gitignored — contains the ClientToken used to derive the AES key). [Core/ConnectionPump.cs](Core/ConnectionPump.cs) is a multi-worker striped poller against LiteNetLib's UDP event queue with storm-protected reconnect. [Core/RateLimiter.cs](Core/RateLimiter.cs) is a token bucket (600 burst / 120 rps); [Core/CircuitBreaker.cs](Core/CircuitBreaker.cs) is CAS-based — both gate outgoing traffic per connection.

## ToolRegistry is the spine

[Core/ToolRegistry.cs](Core/ToolRegistry.cs) is the single source of truth for the MCP tool catalog (schema, required args, descriptions). Three derived artefacts must agree with it, and static tests enforce this on every PR:

1. **`tests/MTTextClient.Tests/_expected/tools.minimum.json`** — locked tool baseline. A name or required-arg disappearing fails `ToolCatalogStaticTests`.
2. **`tests/MTTextClient.Tests/_expected/commandlines.snapshot.json`** — per-tool dispatcher CLI string. Regenerate with `dotnet run --project tools/DispatcherSnapshotGenerator -c Release`. `DispatcherSnapshotTests` re-runs the generator in-process and asserts byte-equality.
3. **The autogenerated table in [README.md](README.md)** between `<!-- BEGIN AUTOGENERATED REGISTRY TABLE -->` markers. Regenerate with `dotnet run --project tools/RegistryReadmeGenerator -c Release`. `ReadmeParityTests` validates parity.

Do **not** hand-edit those three artefacts — re-run the generators. Do **not** put production source under `tests/` or `tools/`; the csproj globs in [MTTextClient.csproj](MTTextClient.csproj) exclude them, but a stray `Main` slipped into either tree will collide with `Program.cs`.

Because the README table is generated from `ToolRegistry.cs` description strings, **any text you write in a tool description ships into the public README on the next regeneration** — review descriptions for user-facing tone.

### Adding a new MCP tool

Minimum touch list:

1. `Core/ToolRegistry.cs` — `yield return Tool(...)` in the right section.
2. `MCP/McpServer.cs` — `MapToolToCommand` switch case. Missing entries are caught by `RegistrationConsistencyTests`.
3. `tests/MTTextClient.Tests/_expected/tools.minimum.json` — add `{name, required[]}`.
4. Re-run both generators (snapshot + README) and commit the updated files.
5. Add a `[SkippableFact]` covering the happy path under `tests/MTTextClient.Tests/Tools/`.
6. If destructive, declare `confirm` in `inputSchema.required` AND add the name to `ConfirmRequiredTools` in `Static/ConfirmGateStaticTests.cs`.

## ConfirmGate

Tools that mutate state declare `confirm` in `inputSchema.required`. [Core/ConfirmGate.cs](Core/ConfirmGate.cs) enforces this at the JSON-RPC boundary; absent `confirm:true` callers get `-32602` echoing the request id. `Static/ConfirmGateStaticTests.cs` keeps a declarative list of which tools must be confirm-gated — when you change a tool's destructiveness, update both the registry schema and that test together.

ConfirmGate is a caller-intent gate, not a security boundary. Do not describe it as trade-risk management or account safety.

## Test categories

| Category    | MTCore needed | Env vars | In PR-gate CI |
|-------------|:-------------:|----------|:-------------:|
| `Static`    |      no       | none | yes |
| `Unit`      |      no       | none | yes |
| `Smoke`     |     yes       | `MTC_TESTING_ENV=1` | no |
| `BenchAll`  |     yes (across all configured profiles) | `MTC_TESTING_ENV=1` | no |
| `LiveTrade` |     yes       | `MTC_TESTING_ENV=1` AND `MTC_LIVE_TRADES=1` | no |

- **Static**: no MTCore, no network, no subprocess. Proves schema, generated-artefact parity, README parity, routing shape.
- **Unit**: in-process behaviour only.
- **Smoke / BenchAll / LiveTrade**: must hit a real MTCore. Do not introduce a mock MTCore for these categories.

Passing one category does not establish coverage of another.

### LiveTrade is destructive on purpose

LiveTrade tests place LIMIT orders at or near market so they actually fill, and **cleanup is absent by design** — the resulting fills populate MTCore's Firebird DB, which the reports-family tools (`mt_reports_query`, `mt_reports_dates`, `mt_reports_comments`, etc.) read from. Wiping the DB resets that foundation. Assertions target FILLED / PARTIALLY_FILLED and the matching `mt_reports_trades` entry, not a "cancelled" terminus. Never set `MTC_LIVE_TRADES=1` against a non-disposable profile.

## Apple Silicon — MTShared.dll PE patch

`lib/MTShared.dll` ships from upstream built as x64 (`Machine=0x8664`). On Apple Silicon the .NET 8 CLR refuses to load that as a native dep. The repo ships the DLL already patched to ARM64 (`Machine=0xAA64`); the managed IL is AnyCPU and JITs fine. The `PatchMTSharedArm64` MSBuild target in [MTTextClient.csproj](MTTextClient.csproj) re-runs [scripts/patch_mtshared_arm64.py](scripts/patch_mtshared_arm64.py) after every macOS build as an idempotent safety net (no-op on Linux/Windows). A vendor refresh of `MTShared.dll` re-introduces 0x8664; the next macOS build flips it back automatically. Missing `python3` downgrades the post-build target to a warning rather than a build failure.

`BouncyCastle.Cryptography` is pinned to `2.0.0` — it is the AES256 implementation that `MTShared.dll`'s crypto path resolves to. `Static/BouncyCastleVersionPinTests.cs` enforces the pin at runtime. Do not bump without verifying the wire-protocol crypto path still loads.

## Environment variables

| Variable | Used by |
|---|---|
| `MTC_TESTING_ENV=1` | Smoke / BenchAll / LiveTrade — gate that prevents test runs from blasting unprepared environments. |
| `MTC_LIVE_TRADES=1` | LiveTrade only; tests that place real orders refuse to run without it. |
| `VAULT_ADDR`, `VAULT_TOKEN` | `mt_vault_*` tools (HashiCorp Vault credential storage). |
| `MT_NATS_UDP_HOST` | Optional NATS UDP event bridge for external event consumers. |

## Public-artefact hygiene

This repo is public. When you write or edit anything that ships in git — code comments, `Core/ToolRegistry.cs` descriptions (which flow into `README.md`), test docstrings, CI workflow comments, CHANGELOG entries, docs — keep out: local filesystem paths, developer/team role terminology, internal planning labels, internal bug-tracker IDs, and references to private planning or review documents. Only the work itself should be visible.
